# 5K Video API 性能检查报告

测试日期：2026-10-29（Asia/Bangkok）  
测试位置：中台服务器回环网络 `127.0.0.1:4010`  
数据库：PostgreSQL 16，约 20 万条分析事件

## 测试范围

- 对全部安全只读接口进行串行多轮延迟测试。
- 对登录、游客、用户资料、收藏、进度、后台增删改、产品发布、分析上报和频率限制执行 16 组自动化集成测试。
- 未在线上压测删除、永久删除、发布、采集启动、截图生成和上传接口，避免改变正式业务数据。
- 在线 OpenAPI 共登记 64 条路径；文件流和 HLS 分片性能取决于源站及视频大小，不与 JSON API 混合统计。

|---|---:|---:|
| `/health` | 3ms 内 | 2–3ms |

| 视频列表/详情 | 5ms 内 | 2–5ms |
| 采集视频列表 | 7ms 内 | 4–7ms |
| 后台产品线列表 | 10ms 内 | 5–6ms |

| 采集首页 bootstrap | 首次生成后缓存 | 13–20ms |

## 已完成优化

1. 将落地页分析从按日期重复扫描全部事件改为单次分组聚合。
2. 曼谷日期计算改为固定 UTC+7 快速日期键，减少大量 `Intl.DateTimeFormat` 调用。
3. 落地页分析、IP明细和综合数据概览增加 30 秒结果缓存。
4. 采集分类数量增加内存缓存。
5. 首页 bootstrap 分类数据改为单次分组，不再按每个分类重复扫描全部视频。
6. PostgreSQL 写入批量合并；分析事件只追加新记录。

## 剩余优化建议

综合数据概览冷缓存约 3.2 秒，是当前唯一明显的计算热点。下一阶段应建立 PostgreSQL 每日聚合表，按分钟或小时增量写入 PV、UV、播放、安装、留存等指标。后台查询直接读取日聚合结果，冷缓存也可稳定在 100ms 内。

采集 bootstrap 和专题推荐首次生成仍受约 7 万条采集目录解析影响。当前生成后均有缓存，常态访问已达毫秒级。若需要无冷启动等待，可在采集任务完成后同步生成静态 bootstrap/topics 文件，而不是等首个用户请求时计算。

## 数据迁移审计

使用 `npm run db:audit-runtime` 逐表核对 JSON 迁移源中的每个主键。12 张业务表 `missing=0`；PostgreSQL 中播放进度和分析事件数量更多，属于切换后新增数据。
