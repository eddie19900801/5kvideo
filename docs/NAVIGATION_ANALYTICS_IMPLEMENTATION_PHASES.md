## 2. 总体实施原则

### 2.1 先底层、后页面

开发顺序必须为：

```text
数据定义
→ 数据库结构
→ 事件采集
→ 聚合查询
→ 后台页面
→ 灰度切换
```

禁止先修改后台展示，再临时拼接旧统计数据。

### 2.2 新旧系统并行

- 新事件系统上线后保持新旧双写。
- 新后台先作为灰度入口。
- 新旧数据至少连续对账 7 天。
- 指标误差符合验收标准后，才能停止旧结构写入。

### 2.3 可回滚

每个阶段必须具备：

- 数据库备份。
- 上一版本代码包。
- 独立功能开关。
- 数据迁移记录。
- 明确的回滚步骤。

### 2.4 统一数据口径

所有模块统一使用以下定义：

- PV：有效页面访问事件数量。
- UV：按日去重的匿名访客数量。
- 会话：30 分钟无行为后重新生成的访问会话。
- 展示：内容至少 50% 进入可视区域并持续 500ms。
- 唯一展示：同一访客、同一天、同一内容只计算一次。
- 点击：通过有效内容交互产生的点击事件。
- 唯一点击：同一访客、同一天、同一内容只计算一次。
- CTR：点击数除以展示数。
- UV CTR：唯一点击数除以唯一展示数。

### 4.3 核心字段

```text

visitor_hash
```

### 4.4 数据关系

```text
站点 sites
 ├─ 导航渠道 nav_channels
 ├─ 分类 categories
 │   └─ 内容 content_items
 ├─ 广告位 placements
 │   └─ 广告素材 creatives
 │       └─ 产品 products
 └─ 应用包 app_packages
```

一次行为事件可以同时关联：

- 一个站点。
- 一个导航来源渠道。
- 一个广告投放渠道。
- 一个分类。
- 一个广告位。
- 一个内容或素材。
- 一个产品。

### 4.5 数据库约束

- 站点域名唯一。
- 导航渠道号唯一。
- 广告渠道号唯一。
- 内容必须关联有效类型。
- 聚合表使用联合唯一键。
- 事件 ID 唯一，防止重复上报。
- 所有外键字段建立查询索引。
- 所有时间字段使用统一时区或 UTC 存储。

### 4.6 数据保存策略

| 数据类型 | 保存周期 |
|---|---|
| 原始行为事件 | 30天 |
| 错误明细 | 30天 |
| 小时聚合 | 90天 |
| 每日聚合 | 长期 |
| 配置和发布记录 | 长期 |

不保存：

- 原始 IP。
- 完整 User-Agent。
- 无上限增长的访客数组。
- 无上限增长的唯一点击数组。

### 4.7 数据库迁移机制

- 所有结构变化必须具有版本号。
- 迁移脚本必须可重复执行。
- 每个迁移记录开始时间、结束时间、处理数量和错误。
- 大数据迁移必须分批执行。
- 不允许启动时同步执行耗时迁移。
- 迁移失败不得导致线上 API 无法启动。

### 5.3 架构职责

#### Domain

保存业务实体、值对象和业务规则，不依赖 HTTP、页面或具体数据库。

#### Service

负责渠道归因、事件接收、聚合、报表和发布流程。

#### Repository

负责数据读取和写入，页面及路由不得直接操作数据库。

#### Interface

负责 HTTP 参数、鉴权、响应格式、SDK 和定时任务入口。

### 5.4 统一内容模型

图标、Banner、交友、弹窗和底部飘窗统一为 `content_item`，通过类型区分：

```text

```

- ID

- 分类
- 排序
- 上架状态
- 推荐状态
- 产品 ID
- 广告位 ID

各类型独有字段放入经过验证的扩展配置，不在页面中临时拼接。

### 5.5 统一事件

只保留：

- `page_view`
- `category_view`
- `content_impression`
- `content_click`
- `search`
- `landing_view`
- `download_click`
- `download_start`
- `app_install`
- `app_launch`
- `load_error`

每条事件必须包含：

- 事件 ID。
- 事件时间。
- 站点 ID。
- 导航渠道 ID。
- 首次渠道 ID。
- 访客 ID。
- 会话 ID。

内容事件额外包含：

- 内容类型。
- 内容 ID。
- 分类 ID。
- 广告位 ID。
- 产品 ID。
- 广告渠道 ID。

### 5.6 客户端上报

- 事件进入浏览器内存队列。
- 每 2 秒或累计 20 条时批量上报。
- 页面离开时使用 `navigator.sendBeacon`。
- 不支持时使用带 `keepalive` 的 `fetch`。
- 短暂失败最多重试两次。
- 不阻塞图片、导航内容和广告展示。

### 5.7 渠道归因服务

统一由 `AttributionService` 处理：

- 验证渠道号。
- 写入首次渠道。
- 更新最近渠道。
- 处理自然流量。
- 处理未知渠道。
- 生成下载归因 ID。
- 向广告 SDK 和落地页传递渠道。

## 6. 第四阶段：历史数据迁移与聚合系统

### 6.1 阶段目标

将现有统计数据迁入新结构，并建立稳定的小时和每日聚合机制。

### 6.2 历史数据映射

| 旧结构 | 新结构 |
|---|---|
| `traffic.daily` | 站点每日访问 |
| `traffic.channelDaily` | 导航渠道每日访问 |
| `analytics.iconDaily` | 图标内容每日统计 |
| `analytics.elementDaily` | Banner、弹窗、交友每日统计 |
| `adCenter.daily` | 广告投放每日统计 |
| `appPackageDaily` | 落地页、下载、安装和启动 |
| `searchAnalytics` | 搜索词每日统计 |

### 6.3 迁移规则

- 无法识别站点的数据归入 `LEGACY_SITE`。
- 没有渠道的数据归入 `NATURAL`。
- 非法渠道归入 `UNKNOWN`。
- 只有总量、没有访客明细时，不生成虚假的 UV 明细。
- 历史数据保持原有统计数值，并标记数据来源为 `legacy`。
- 每批迁移后自动生成对账结果。

### 6.4 聚合任务

#### 增量聚合

每 5 分钟处理最近 15 分钟事件。

#### 日终重算

每天 00:10 重新计算上一日数据，修正延迟事件。

#### 数据清理

- 03:00：删除超过 30 天的行为明细。
- 03:30：删除超过 90 天的小时聚合。
- 04:00：执行数据库维护和压缩。

### 6.5 聚合任务安全要求

- 同一任务只能有一个实例执行。
- 每批记录处理游标。
- 任务中断后从游标继续。
- 聚合使用 UPSERT，不重复累加已处理事件。
- 失败记录错误并告警，不删除原始事件。

## 8. 第六阶段：灰度切换、清理和性能优化

### 8.1 阶段目标

完成新旧系统切换，移除无效功能，降低数据库体积并验证回滚能力。

### 8.2 灰度步骤

1. 新旧事件和聚合系统同时运行。
2. 管理员先使用新后台入口。
3. 连续 7 天生成自动对账报告。
4. 修复自然流量、未知渠道和跨站点归因差异。
5. 将新后台切换为默认入口。
6. 保留旧后台隐藏入口一个发布周期。
7. 停止旧数据结构写入。

### 8.3 清理内容

- 旧的统计总计字段。
- 大型访客数组。
- 大型唯一展示和唯一点击数组。
- 投放计划前端页面。
- 投放计划 API。
- 重复的统计查询接口。
- 已合并的旧菜单组件。
- 无调用的兼容代码。

删除前必须确认：

- 已完成完整备份。
- 新系统已连续稳定 7 天。
- 旧结构不再写入。
- 回滚包可以恢复旧版本。

### 8.4 性能优化

- 执行数据库压缩。
- 对历史聚合分区或归档。
- 后台查询增加慢查询记录。
- 大型导出改为异步任务。
- 发布操作主动清理配置缓存。
- 统计缓存和配置缓存分离。

- 新增站点和渠道不需要修改统计代码。

## 9. 阶段依赖关系

```text
第一阶段：审计和基线
        ↓
第二阶段：数据库架构
        ↓
第三阶段：代码架构和事件系统
        ↓
第四阶段：迁移和聚合
        ↓
第五阶段：后台重构
        ↓
第六阶段：灰度、清理和优化
```

第二阶段数据库模型通过评审前，不进入第三阶段。

新事件和聚合接口完成前，不进入第五阶段后台页面开发。

新旧数据未连续对账 7 天前，不执行第六阶段旧数据清理。

## 11. 总体验收结果

```text
选择日期

→ 查看该渠道的 PV、UV 和会话

```
